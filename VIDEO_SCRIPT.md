# Текст к видео (озвучка)

Живой текст, читается вслух. В квадратных скобках — что делать на экране.
Числа взяты из реального прогона, не выдуманы.

---

## Интро

Так, задача. У меня есть docx — «Война и мир», четыре с лишним миллиона символов.
Хочу засунуть его в Milvus и потом по нему искать. Покажу два способа поиска — по словам
и по смыслу — плюс веб-интерфейс Attu, через который это всё видно и настраивается.

Сразу расшифрую два названия, чтобы не было тумана.

**Milvus** — это база данных, но не совсем обычная. Обычная база ищет по точному значению:
«дай строку, где id равно пяти». Milvus — векторная база: она ищет по похожести. Ты скармливаешь
ей текст запроса, а она находит куски, близкие по содержанию.

**Attu** — это веб-морда к Milvus. Сама база — это сервер без картинок. Attu даёт интерфейс:
посмотреть, что внутри, запустить поиск, настроить модель. Можно работать и из кода, но глазами
понятнее.

И ещё три слова, которые дальше будут постоянно, — запомни их сразу:

- **коллекция** — аналог таблицы в обычной базе. Один документ — обычно одна коллекция;
- **чанк** — кусок текста. Целую книгу в базу не кладут: её режут на куски по несколько сотен
  символов, и каждый такой кусок — чанк;
- **вектор**, он же эмбеддинг — набор чисел, которым модель описывает смысл текста.
  Подробно разберём в шаге 5.

Всё на Docker. Kubernetes не нужен, ничего собирать не надо — образы готовые.

## Шаг 2. Поднимаем базу

Одна команда.

```powershell
docker compose up -d
```

Поднимается четыре контейнера. Контейнер — это как маленькая виртуалка с уже собранной программой
внутри: скачал образ, запустил, работает. Ничего ставить руками не надо.

- **milvus** — сама база, наша главная;
- **etcd** — служебная база. Milvus хранит в ней свою внутреннюю информацию: какие коллекции есть,
  какие индексы, кто подключён. Мелкая, но без неё никак;
- **minio** — файловое хранилище. Туда Milvus складывает сами данные;
- **attu** — веб-интерфейс.

Нам важен в первую очередь milvus, остальные три — его обвязка.

[Пауза 1–2 минуты, потом]

```powershell
docker compose ps
```

Вот ключевой момент. Ждём, пока `milvus-standalone` станет **healthy**. Не «Up», а именно
healthy — это значит, база реально готова принимать запросы. У меня вот три healthy,
а Attu просто Up — ему healthcheck не прописан, это нормально, не пугайся.

`healthy` — это проверка, которую Docker сам периодически делает внутри контейнера: заходит
и спрашивает «жив ли ты?». Если отвечает — пишет healthy. То есть слово healthy — это не
просто «запустился», а «сам подтвердил, что готов работать». Отсюда и подсказка: если
milvus минут пять не healthy, можно кликнуть прямо в выводе на ссылку логов.

Если `milvus-standalone` висит не healthy больше пары минут — почти всегда мало памяти
в Docker. Ему надо гигабайт шесть минимум.

## Шаг 3. Заходим в веб-интерфейс

[Открыть браузер]

```
http://127.0.0.1:13000
```

И тут первое место, где все спотыкаются. **Логинов два, и они разные.**

Первый — вход в саму Attu. Это учётка веб-интерфейса, к базе она отношения не имеет:
```
admin / AttuDemo123!
```

Второй — подключение к Milvus. Вот тут адрес `milvus:19530`. Именно `milvus`, а не `127.0.0.1`.
Потому что Attu стучится в базу изнутри своей докер-сети, где база зовётся по имени сервиса.
Логин `root`, пароль `MilvusDemo123`.

Что вообще значит `19530` — это порт. Просто число, по которому процесс внутри себя принимает
соединения. В обычной жизни ты его не замечаешь, но в Docker приходится: у каждого контейнера
свои порты, и чтобы ты попал снаружи, порт контейнера пробрасывают на порт твоего компьютера.
Вот в `docker compose ps` ты и видел `0.0.0.0:13000->3000` — это значит «порт 13000 на компе
смотрит во внутрь контейнера, на его порт 3000». Поэтому Attu у меня на 13000, хотя внутри
работает на 3000. А 19530 — это порт самого Milvus, он проброшен один в один.

[Нажать Connect]

Если вверху справа увидишь «Connection Unavailable» — значит адрес или пароль не те.
Это буквально самая частая ошибка: люди пишут 127.0.0.1 и удивляются.

## Шаг 4. Что вообще в интерфейсе

Слева — список коллекций. Коллекция в Milvus — это по сути таблица: строки и колонки.
Только колонки тут называются полями, и одно из полей обязательно векторное.

[Показать список]

У меня их несколько. Смотри на две: `voina_i_mir` — векторная, и `voina_i_mir_ft` — та же книга,
но залитая под поиск по словам. Почему две — сейчас дойдём, это и есть суть.

Если открыть любую коллекцию, у неё внутри такой набор полей:

- `id` — номер строки, как в обычной таблице;
- `chunk_index` — какой это по счёту кусок текста. Нужен, чтобы сохранить порядок: книга-то
  порезана, а собрать обратно надо в правильной последовательности;
- `source` — из какого файла приехал кусок;
- `content` (или `text`) — сам текст куска, то, что мы будем читать в результатах;
- и векторное поле — `vector` или `sparse`. Вот в нём и лежит «смысл» в виде чисел.

Внутри коллекции три вкладки:

- **Data** — просто строки, можно глазами посмотреть, что лежит;
- **Query** — сам пишешь фильтр, типа «дай чанки с 10 по 20»;
- **Search** — собственно поиск.

[Открыть меню коллекции — три точки]

Ещё Load и Release. Тут момент, который многих путает. Данные коллекции лежат на диске, но чтобы
по ним искать, коллекцию надо «поднять в память» — это и есть Load. Пока не загружена, она ищет
очень плохо или вообще не ищет. Если видишь пометку Not Loaded — жми Load.

[Открыть шестерёнку]

И настройки. Там два раздела, которые нам пригодятся: **Embeddings** и **LLM Configuration**.
Про них дальше.

## Шаг 5. Заливаем документ

Тут два способа, и это самое главное для понимания темы.

### Способ первый — вообще без моделей

[Терминал]

```powershell
python .\scripts\docx_to_milvus_bm25.py --file ".\samples\voina-i-mir.docx" `
  --collection voina_i_mir_ft --user root --password MilvusDemo123 --recreate
```

Прежде чем читать вывод — расшифрую команду, потому что такие длинные строки пугают, а тут
всё логично. Это питоновский скрипт из папки `scripts`, поэтому сначала слово `python`, потом
путь к файлу через `.\`. Дальше идут **флаги** — параметры, каждый начинается с двух дефисов
и говорит скрипту, что делать:

- `--file` — какой файл читать, тут «Война и мир»;
- `--collection` — под каким именем создать коллекцию, то есть имя таблицы;
- `--user` и `--password` — логин и пароль от Milvus, те же, что в Attu;
- `--recreate` — если коллекция уже есть, снести её и сделать заново. Без этого флага скрипт
  просто доложит строки в старую, и получится каша.

Скрипт берёт docx, режет текст на куски примерно по восемьсот символов и складывает в коллекцию.
Модель не нужна вообще. Milvus сам строит так называемый BM25-индекс.

Про docx: это просто zip-архив, внутри которого лежит текст в виде XML. Поэтому скрипту
достаточно распаковать его и вытащить абзацы. Сам Word при этом не нужен — файл читается
библиотекой python-docx, которая уже установлена.

Теперь что такое BM25. Это классический поисковый алгоритм, лет ему уже десятки. Работает просто:
смотрит на слова и считает, насколько кусок текста похож на запрос — чем чаще в куске встречаются
слова из запроса, тем выше он в выдаче. Ещё учитывает, что редкие слова важнее частых, и что
в длинном куске совпадение «размазано». Ровно такой же принцип внутри Википедии и вообще почти
в любом текстовом поиске. Никаких нейросетей, чистая статистика слов — поэтому быстро и без модели.

Технически Milvus под капотом превращает текст в «разреженный вектор» — тот самый `sparse`,
где отмечено, какие слова есть и как часто. Но для нас это деталь: снаружи это просто
поиск по словам.

[Показать вывод]

Смотри: двадцать три тысячи блоков, шесть тысяч шестьсот пятьдесят семь чанков. Семь секунд.
Всё.

Искать в такой коллекции можно только по словам. Запрос «дуэль Долохова» найдёт куски, где
эти слова есть. А напиши «поединок» — не найдёт, потому что слово другое. Это не баг, это
природа метода.

### Способ второй — с моделью эмбеддингов

```powershell
python .\scripts\vectorize_docx.py --file ".\samples\voina-i-mir.docx" --collection voina_i_mir `
  --user root --password MilvusDemo123 --embedder api `
  --api-base http://127.0.0.1:1234/v1 --api-key "<токен>" `
  --api-model text-embedding-nomic-embed-text-v1.5 --batch 64 --recreate
```

Здесь каждый чанк прогоняется через модель, которая превращает текст в вектор — набор чисел.
У меня это `nomic-embed-text-v1.5`, семьсот шестьдесят восемь чисел на кусок, крутится
локально в LM Studio. Ноль токенов, никуда не ходим.

Поясню, что тут вообще происходит. Модель читает текст и выдаёт список чисел — у нас 768 чисел
на кусок. Представь, что это координаты точки в пространстве с 768 осями. Только не в обычном
трёхмерном, а в очень многомерном — представить нельзя, но математика та же. Смысл в том, что
похожие по содержанию тексты получают близкие координаты, а разные — далёкие. «Дуэль» и «поединок»
окажутся рядом, хотя это разные слова. «Война» и «бал» — далеко. Модель ловит смысл, а не буквы.

Вот отсюда и берётся поиск по смыслу: мы ищем текст, чей вектор ближе всего к вектору запроса.

Заметь: это не языковая модель вроде чата. Она ничего не пишет, она только считает числа.
768 — это просто длина списка, размерность. Лежат эти числа в векторном поле `vector`,
и при поиске сравниваются именно они.

[Показать вывод]

Тут дольше: сорок восемь секунд на эмбеддинги, всего около минуты. Логично — каждый чанк надо
через модель прогнать, в этом вся разница с первым способом.

Зато такая коллекция ищет **по смыслу**. Спрашиваешь «казаки атакуют французов» — находит куски
про нападение на французов, даже если слова «казаки» там рядом нет. Модель понимает, что это
одно и то же по сути.

Важно: это два разных типа коллекции. В векторную нельзя засунуть текст без эмбеддингов,
а BM25-коллекция не умеет искать по смыслу. Поэтому я и залил книгу дважды.

## Шаг 6. Поиск

### По словам

[Открыть voina_i_mir_ft → Search]

Открываю коллекцию. Search. Add a search request. Тип — **Full-Text**. По-русски это
«полнотекстовый поиск», то есть поиск по словам, тот самый BM25. Text Field — `text`, это поле,
в котором ищем. Пишу «Бородинское сражение». Search.

[Показать результат]

Вот. Самый верхний — чанк три тысячи четыреста семьдесят третий, про Понятовского и Утицу.
Это реально про Бородино, метод не ошибся.

Рядом с каждым результатом стоит число — это **score**, оценка релевантности. Чем больше, тем
лучше совпадение. У BM25 это не проценты: там счётчик вида «сколько раз встретились слова
запроса, с поправкой на редкость». Значение 15 — это не «15 процентов», просто внутренний
балл, сравнивать надо только между собой: 15.5 лучше, чем 9.4.

Обрати внимание на скорость — миллисекунды. Потому что сравниваются слова, ничего не считается.

[Попробовать «Наташа Ростова»]

И ещё, для наглядности.

### По смыслу

Тут сначала надо один раз настроить. Это грабли номер два после логинов, многие тут застревают.

[Settings → Embeddings → Add Provider]

Провайдер `OpenAI`, base URL `http://host.docker.internal:1234/v1`, модель та же, что при
заливке — `nomic-embed-text-v1.5`, размерность `768`. Test, Save.

Без этого шага поле Similarity Text будет серое, и поиск просто молча не заработает.

[Открыть voina_i_mir → Search]

Теперь: тип Vector, поле `vector`, переключаю на **Similarity Text** — то есть ввожу словами,
а Attu сам посчитает вектор запроса. Пишу «казаки атакуют французов». Metric COSINE. Search.

Про метрику. Метрика — это способ измерить близость двух векторов. COSINE считает угол между ними:
чем меньше угол, тем ближе по смыслу. Значение уходит от нуля к единице, ближе к единице — почти
одно и то же. Для текстов обычно берут именно COSINE, потому что он не зависит от длины текста —
длинный кусок и короткий запрос сравниваются честно. Второй популярный вариант — L2, обычное
расстояние, но для текстов он хуже.

[Показать]

Смотри, что нашлось. Про нападение на французов — а слова «казаки» в этих кусках нет вообще.
Вот это и есть поиск по смыслу.

Здесь то число рядом с результатом — это уже **не score, а distance**, метрика COSINE. Она
ведёт себя наоборот: 1.0 — это полное совпадение смысла, а меньше — менее похоже. Не путай с
предыдущим случаем, где больше значило лучше. Тут чем БЛИЖЕ к единице, тем лучше. У меня
0.82 — это очень сильное совпадение, на практике совпадения выше 0.75 считаются хорошими.

И запомни: модель запроса должна совпадать с моделью, которой заливали. Если заливал
nomic — значит и здесь nomic. Иначе вектора будут в разных пространствах, и результат будет мусор.

### Посмотреть документ вообще без поиска

Есть и третий вариант — просто пройтись по тексту.

[Открыть voina_i_mir → Query]

Вкладка Query. Фильтр `chunk_index < 10`, поля `chunk_index, content`. Query.

[Показать]

Вот первые десять чанков: титул, предисловие издания. Меняю фильтр на `chunk_index >= 10 and
chunk_index < 20` — иду дальше. Так можно тупо листать документ и смотреть, что там лежит.

### Про LLM — коротко

Если хочется не куски текста, а готовый ответ словами — есть панель AI-агента. Ему нужна
настроенная LLM в Settings → LLM Configuration.

Но держи в голове: LLM и эмбеддинги — это разные вещи. Эмбеддинги текст превращают в вектор
для поиска. LLM пишет ответ. Для поиска LLM не нужна вообще, и дальше я её не трогаю.

## Шаг 7. Выгружаем документ назад

[Терминал]

```powershell
python .\scripts\milvus_export.py --collection voina_i_mir --out voina_back.docx --format docx `
  --user root --password MilvusDemo123
```

Milvus хранит исходный текст чанков, поэтому его можно достать обратно. Формат — txt, docx
или jsonl, на выбор. Скрипт сам находит текстовое поле и сортирует по `chunk_index`, чтобы
порядок был правильный.

Про форматы, чтобы было понятно, что выбирать. **txt** — просто текст, открывается везде.
**docx** — тот же текст, но в обёртке от Word, один абзац на чанк, из-за этого файл большой.
**jsonl** — одна строка на чанк в формате JSON, то есть машиночитаемый: каждая строка
отдельно валидный объект с текстом и номером. Его удобно скормить обратно в заливку или
в другую программу. Выбор тут только в том, куда ты пойдёшь с результатом дальше.

[Открыть выгруженный файл в Word]

Вот он. Пятьдесят девять тысяч абзацев, открывается нормально.

Но скажу честно, без иллюзий. Это **не** восстановление документа. Вернётся плоский текст.
Вёрстка, картинки, таблицы, колонтитулы — ничего этого не будет, потому что в базе лежит
только текст чанков. Для поиска это нормально, как бэкап документа — нет.

То же самое можно сделать руками из интерфейса: меню коллекции → Export Data.

## Финал

Коротко, что унести из видео.

Первое. Способа заливки два. BM25 — без моделей, семь секунд на всю книгу, ищет по словам.
Эмбеддинги — около минуты, ищет по смыслу. Это разные коллекции, и модель запроса должна
совпадать с моделью заливки.

Второе. В Attu два разных логина: свой у веб-интерфейса и свой у Milvus. В подключении адрес
`milvus`, а не `127.0.0.1`.

Третье. Чтобы искать по смыслу через интерфейс, надо один раз настроить Embeddings в настройках.
Без этого поле будет серое и ничего не произойдёт.

Четвёртое. Выгрузка возвращает текст, но не вёрстку.

[Показать рабочее окно Attu]

Всё, стенд работает. Если что-то не сработало — в девяноста процентах случаев либо

## Словарик (хорошо смотрится кадром в конце)

| Слово | Что это простыми словами |
|-------|--------------------------|
| **Milvus** | векторная база данных. Ищет не по точному совпадению, а по похожести |
| **Attu** | веб-интерфейс к Milvus: посмотреть данные, поискать, настроить модель |
| **Docker** | способ запустить готовую программу в контейнере, без ручной установки |
| **контейнер** | изолированный процесс с программой внутри. Уже собран и готов к запуску |
| **порт** | число, по которому к процессу обращаются снаружи. У контейнера свой, пробрасывается наружу |
| **volume** | постоянное хранилище Docker. Удаляешь контейнер — данные в volume остаются |
| **healthy** | Docker проверил контейнер изнутри и он ответил «жив, готов работать» |
| **коллекция** | таблица в базе. Один документ — обычно одна коллекция |
| **поле** | колонка таблицы: `id`, `content`, `vector` и прочее |
| **чанк** | кусок текста. Документ режут на чанки, чтобы искать по мелким фрагментам |
| **вектор / эмбеддинг** | список чисел, которым модель описывает смысл текста (у нас 768 чисел) |
| **размерность** | сколько чисел в векторе. 768 — это длина списка, не «качество» |
| **модель эмбеддингов** | программа, превращающая текст в вектор. Это не чат-бот |
| **BM25** | поиск по словам без моделей: чем больше слов из запроса, тем выше результат |
| **Full-Text** | то же, что BM25, только так это названо в интерфейсе Attu |
| **Vector** | тип поиска по вектору. Именно он ищет по смыслу |
| **Similarity Text** | поле в Attu: вводишь слова, а он сам считает по ним вектор |
| **COSINE** | метрика близости векторов. Ближе к 1 — похожее |
| **score** | число у результата BM25. Чем больше — тем лучше совпадение |
| **distance** | число у результата COSINE. Чем ближе к 1 — тем лучше (наоборот, не score) |
| **индекс** | служебная структура, ускоряющая поиск. Как алфавитный указатель в книге |
| **Load** | «поднять коллекцию в память». Без этого поиск не работает |
| **LLM** | языковая модель для ответов текстом. Для поиска не нужна |
| **флаг** | параметр команды, начинается с двух дефисов: `--file`, `--recreate` |
| **jsonl** | текстовый файл, где каждая строка — отдельный объект JSON |

## Заметки к съёмке

- Не гнать. Между «набрал команду» и «показал вывод» почти всегда есть пауза — это нормально,
  её можно потом ускорить монтажом, но не вырезать целиком.
- Первую заливку (`voina_i_mir`, минута) лучше показать как есть и сказать «вот, надо подождать»,
  а не молча смотреть в стену.
- Момент с двумя логинами — обязательно проговорить, это самая частая ошибка у людей.
- Если записываешь за один дубль и что-то отвалилось — не переписывай всё, просто скажи
  «вот тут видно, что X не настроен, сейчас исправлю» и покажи фикс. Живее, чем идеальный дубль.
